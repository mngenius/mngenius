✓ MERGE / upserts, partitioning

New vocab to name-drop

• _delta_log = the transaction log (≈ Iceberg metadata/manifests)

• OPTIMIZE + ZORDER / liquid clustering = compaction & clustering

• VACUUM = expire old files (retention)

• Medallion: bronze → silver → gold

Talking point: "I ran Iceberg-on-S3 with snapshot-based time travel and manifest pruning — Delta's _delta_log, OPTIMIZE and time travel are the same ideas."

Governance: Glue Catalog + IAM → Unity Catalog

  • My catalog auto-connected with CDH creds and indexed databases → tables → S3 paths. Unity Catalog does the same as a 3-level namespace catalog.schema.table.
  • External locations + storage credentials = the governed S3-access pattern I already used (no ad-hoc keys).
  • Grants replace IAM policies for table/column/row access; reads open, writes admin-only, audit-logged — exactly my Views governance model.
  • Built-in lineage + data discovery — what I built manually as a catalog index comes for free.
  • Delta Sharing = cross-org sharing without copying (bonus talking point).

Compute: Glue/EMR → Databricks clusters

Cluster types

Job clusters (ephemeral, per-run — like Glue jobs) vs all-purpose (interactive notebooks). Autoscaling + spot.

Photon

Vectorised C++ engine for SQL/DataFrame. The "fast additive SUM" layer — my Athena reaggregation analog.

Serverless

Serverless SQL warehouses = Athena-like zero-ops query; serverless jobs too.

DBUs

Billing unit = Databricks Units × time × tier. The cost lever I'd tune (right-size clusters, spot, auto-terminate).

Cost-control instinct transfers: I parked idle Azure VMs on a schedule; here it's auto-terminate, autoscaling and job vs all-purpose choice.

My pipeline compiler → Delta Live Tables

I built a declarative JSON DSL that a compiler turned into Spark reads + validated outputs. DLT is the same philosophy: declare tables in SQL/Python, the platform builds the DAG, and expectations are my output-contract checks.

My killer story: additive vs non-additive VaR

Additive → cheap

Notional, P&L …

SUM in Databricks SQL / Photon

Pre-aggregate into gold Delta tables or SUM on the fly. Instant.

Non-additive → recompute

VaR / risk vectors …

VaR(book) ≠ Σ VaR(trades)

Re-aggregate risk vectors element-by-element via Spark DataFrame / applyInPandas — the heavy job I already tuned.

This is the story that sells me: I know why you can't just SUM a VaR, and how to do the correct roll-up on Spark. That's a data-correctness insight most candidates miss — platform-independent.

Release rails: my 4 gates → Databricks Asset Bundles

My draft → validated → live + 4 gates becomes DABs (YAML-defined jobs/DLT/notebooks) promoted through dev → staging → prod workspaces, gated by CI + approvals. Same discipline, native tooling.

How to answer "you haven't used Databricks"

  • "Have you used Databricks in production?"
  • "Not the managed platform, but I built the same lakehouse pattern on AWS — Iceberg-on-S3, Glue/Athena, a Spark compiler. It's the same Apache Spark and SQL; the concepts transfer directly."
  • "How would you migrate our pipelines?"
  • "Delta tables for Iceberg, Unity Catalog for Glue Catalog + IAM, DLT/Workflows for my Glue jobs, Asset Bundles for CI/CD. I'd keep the medallion layering and the additive/non-additive split."
  • "What's hard about VaR at scale?"
  • "Non-additive roll-ups: you must recompute from risk vectors, not sum. On Databricks that's a Spark job — the exact optimisation work I've done."
