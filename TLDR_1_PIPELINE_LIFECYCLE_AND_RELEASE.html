Pipeline Lifecycle
& How We Release to Production

TL;DR #1 — Themis doesn't just answer business questions, it ships them through a controlled, tested, auditable path from a designer's screen to production — with guardrails at every step.

1 · The lifecycle in one picture

Three persisted states — draft validated live — plus an ephemeral Explore mode that is never committed.

The three persisted states

StateWhat it meansWho / what touches it
draft Work-in-progress. Auto-saved. Cannot affect production. Editors iterate freely
validated Frozen snapshot that passed full validation. Ready to publish. Reviewer / promoter
live The production version. Runs in AWS Glue, on schedule. Only changes via an explicit promote

Key property — production is never edited in place. Opening a live pipeline branches a new draft from live; the live version keeps running untouched until someone deliberately promotes a replacement.

2 · Versioning — nothing is silently overwritten

  • Draft saves overwrite the current draft (minor bump) — no history pollution from keystroke-level versions.
  • Promotion freezes the record — it becomes an immutable, auditable artifact.
  • Editing a promoted version creates a new major version as a draft — the old live record is preserved intact.
  • Pipelines are portable JSON documents (diffable, versionable) — not opaque code.
  • No arbitrary code execution — expressions are a whitelisted operation tree, never eval().

3 · Four independent safety layers to prod

A change cannot reach a business user without passing all four gates.

What each gate actually enforces

1 · Validation

Per promotion: schema, expressions, sources & an output-contract check. Re-runs a live-data preview before publishing.

2 · Automated tests

CI on every push & PR. 150+ unit tests on the compiler core, run against SQLite & DynamoDB. A red build blocks the merge.

3 · Promotion gate

A distinct, permission-checked action — not a side effect of saving. Access controlled per pipeline on top of Okta.

4 · Deploy gate

Manual per-environment (uat → prod). Prod needs reviewer approval, deploys are componentised, and success is confirmed by polling the live build ID.

4 · Adding a feature is additive

Worked example: "365-day history". We extend the JSON DSL & compiler — we don't rewrite the product.

One-slide summary

  • Draft → Validated → Live, with production never edited in place.
  • Immutable, diffable versions — full audit trail, no silent overwrites.
  • Four gates to prod: in-product validation, automated CI tests, a permissioned promotion, and an approval-gated, build-verified deploy.
  • New features are additive — they ride the same rails.
  • Net: the release process is a feature, not overhead — it keeps a fast-moving analytics tool safe for production risk numbers.
